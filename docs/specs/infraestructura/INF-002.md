# INF-002 — Test de punta a punta (E2E) del recorrido de la demo

**Trello:** no tiene tarjeta propia. Lo pide `TESTING_STRATEGY.md` (nivel E2E de la pirámide) y `ENGINEERING_STANDARDS.md` (stack: "Playwright (flujo de la demo)").

## Historia de usuario
COMO equipo de desarrollo QUIERO un test automático que recorra la app como en la demo (ingresar, filtrar, ficha, comparar y seguimiento) PARA enterarnos antes del Demo Day si un cambio rompe el recorrido que vamos a mostrar.

## Contexto
- Los tests de backend (pytest) y de frontend (Vitest) prueban cada pieza por separado, con la API mockeada en el frontend. Ninguno prueba que el build de React y FastAPI anden juntos contra una base real.
- `TESTING_STRATEGY.md` pide **un** test E2E del recorrido, contra el seed fijo `backend/semillas/demo_e2e.py` y no contra datos sincronizados. El seed ya existe (lo agregó INF-001, con sus tests en `tests/*/test_inf001_demo_e2e.py`); falta el test.
- El seed carga datos reales grabados, sin llamar a ninguna API: Liga Profesional 2026 (21 jugadores, cobertura completa), Primera Nacional 2025 (22 jugadores, básica), los valores de mercado de la muestra de Transfermarkt y el usuario demo. En Buscar se ven **40 resultados** (los que tienen estadística vigente, RN-017).

## Criterios de aceptación

Es **un solo test**, con un paso (`test.step`) por pantalla, para que el reporte diga en qué paso se rompió. Corre en Chromium con una ventana de escritorio de 1280 × 800 (la tabla de Buscar de UI-002; las tarjetas de menos de 768 px quedan fuera).

## Cómo se levanta la app para el test
- **Igual que en producción:** FastAPI sirve el build de React (`npm run build`, ADR-0003) en `http://localhost:8000`. Así el test prueba el mismo origen, la cookie y el ruteo del SPA (`backend/app/frontend.py`) que usa Render.
- **Base:** la base local de desarrollo (`statsline_dev`), con las migraciones aplicadas y el seed `python -m semillas.demo_e2e`. El seed se niega a correr contra un host que no sea local o con `ENTORNO=produccion` (`verificar_base_local`), así que nunca toca Aiven.
- **El test no levanta nada:** asume la app levantada, como dice `TESTING_STRATEGY.md` ("app levantada"). Antes de empezar pide `/api/v1/salud`; si no responde, falla con un mensaje que dice qué levantar y remite a `SETUP.md`.
- **Otra URL:** `E2E_URL` permite correrlo contra Vite (`http://localhost:5173`, con uvicorn atrás) o contra otro puerto.
- **Contraseña:** el test la lee de `DEMO_CONTRASENA`. Si la variable no está en el entorno, `playwright.config.ts` toma solo esa variable de `backend/.env` (con `util.parseEnv` de Node, sin dependencias nuevas). No se escribe en el código, ni en los logs, ni en el reporte. Por eso el trace de Playwright queda **apagado** (guarda el texto que se escribe en cada campo) y, si falla, solo se guardan captura y video, donde el campo de contraseña se ve enmascarado. Al implementar se verifica que la contraseña no aparezca en ningún archivo de `test-results/` ni de `playwright-report/`.
- **Repetible:** se puede correr varias veces seguidas sin volver a cargar el seed. Antes del recorrido, el test asegura por la API que M. Rojo no esté en la lista de seguimiento del usuario demo (`DELETE /seguimiento/{id}`, idempotente), por si una corrida anterior se cortó a la mitad. No toca a ningún otro jugador de la lista.

## Cómo se corre en local

```bash
# 1. Base local con el seed (una vez; se puede repetir)
cd backend && source .venv/bin/activate
alembic upgrade head
python -m semillas.demo_e2e

# 2. App con el build de React
cd ../frontend && npm run build
cd ../backend && uvicorn app.main:app            # http://localhost:8000

# 3. En otra terminal, el test
cd frontend
npx playwright install chromium                  # solo la primera vez
npx playwright test
```

## Qué pasa si falla
- El reporte de la consola dice qué paso (`Ingresar`, `Filtrar`, `Ficha`, `Comparar` o `Seguimiento`) y qué verificación falló.
- Se guardan una captura y el video de la corrida fallida en `frontend/test-results/` (sin trace, por la contraseña), y el reporte HTML en `frontend/playwright-report/` (`npx playwright show-report`). Las dos carpetas van al `.gitignore`.
- En local no hay reintentos: si falla, falló. En el CI se propone un reintento para no frenar un PR por una demora de red del runner, y el reporte marca el test como "flaky" si pasó al segundo intento.
- Si la app no está levantada o falta `DEMO_CONTRASENA`, el test falla en el primer paso con un mensaje que dice qué falta, en lugar de un timeout.

## Casos borde
- **Dato no disponible:** el paso 2 verifica que un valor de mercado que falta se ve como "Dato no disponible" y no como 0 (RN-008).
- **Corrida cortada a la mitad:** M. Rojo puede quedar en la lista de seguimiento; la limpieza previa por la API lo resuelve.
- **El seed se cargó varias veces:** es upsert y no duplica jugadores, así que los conteos no cambian. Los ids pueden variar entre bases, por eso el test nunca usa ids fijos: navega por nombre y verifica la forma de la URL.
- **Base con datos sincronizados además del seed:** los conteos no coinciden y el test falla. Es esperado: el E2E corre solo contra el seed (`TESTING_STRATEGY.md`).
- **App apagada o sin `DEMO_CONTRASENA`:** falla rápido con un mensaje claro (ver "Qué pasa si falla").
- **Avisos que se van solos:** los avisos duran 4,2 s; el test los busca apenas toca el botón.
